# Pie Hub

Status: proposed; the Hub package, connector, and enrollment commands do not yet
exist. This is the V1 proposal, not a description of shipped behavior.

## Scope and ownership

A public HTTPS **Hub** receives signed GitHub events and asks an enrolled daemon
to fire an existing Schedule. Pi, model credentials, Projects, session history,
and execution stay on the daemon. This supplies the inbound webhook path deferred
by [ADR 0010](../adr/0010-github-pull-request-actions.md).

V1 has one operator and at most one enrolled daemon per Hub organization. An
offline daemon fails closed with `daemon_not_connected`; there is no queue.
GitHub is a Schedule trigger, never a way to create a session without a Schedule
row. Hub must not duplicate the Schedule store, clock, run history, or page.

```text
GitHub → public HTTPS Hub → outbound WebSocket from daemon
                             → ScheduleService.fire → ordinary Pi session
                                                     → local gh write-back
```

| Owner                                         | Responsibility                                                              | Boundary                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `packages/hub` (`@getpie/hub`, bin `pie-hub`) | Webhook signature check, routing, daemon socket, delivery log, operator API | No server/CLI imports, Pi, oRPC, SPA, or workspace access                |
| `packages/server/src/hub/`                    | Enrollment, outbound connector, Schedule dispatch, execution-id mapping     | Does not start Hub or bind a public webhook port                         |
| `packages/pie` (`@getpie/cli`)                | `pie hub login/connect/status/disconnect/logout`                            | Configures the daemon only; no `pie hub serve` or Hub-package dependency |
| `@getpie/contract`                            | Shared Hub wire schemas                                                     | A leaf contract, not a second session API                                |

Hub runs foreground as its own binary. Proposed defaults: port 3000,
`$PIE_HUB_HOME` or `~/.pie-hub` (`~/.pie-hub-dev` in development). This is distinct
from daemon enrollment under `$PIE_HOME/hub/`. The connector starts only when a
relationship exists; normal daemon startup otherwise stays Hub-unaware.

Hub follows the repository's Effect/platform rules: platform services are
provided at its composition root, including WebSocket upgrades. Domain modules
must not import runtime-specific filesystem APIs. The published ESM artifact
must run on Node; a Bun composition root may run the same domain code.

## Identity and security

Three Hub credentials are distinct from the daemon's local UI bearer and tickets:

1. **Operator login**, keyed by Hub origin on the CLI machine, can mint enrollment
   tokens. `pie hub logout` clears only this login.
2. **Enrollment token**, one-time, approximately ten minutes, scoped to
   `daemons:enroll`. The CLI hands it to the daemon and forgets it. Hub keeps unused
   tokens only in memory; restart requires minting again.
3. **Relationship credential**, generated by the daemon, persisted locally with
   mode `0600`, and presented on every Hub socket. Hub stores only its hash.
   It survives CLI logout; disconnect or Hub-side revoke ends the relationship.

Remote origins require HTTPS; cleartext HTTP is loopback-only (`localhost`,
`127.0.0.1`, `[::1]`). Verify GitHub `X-Hub-Signature-256` before interpreting
payload fields. A non-empty `fromUsers` allowlist is mandatory at Hub startup.

Enrollment authorizes allowlisted GitHub users to start worktree sessions on the
machine. Repository routing must resolve a registered Project, never accept a
caller-supplied path or clone an unknown repository. Wrap GitHub context as
untrusted text appended to the Schedule prompt; it cannot replace that prompt,
grant extra Pi tools, or authorize reading session history through Hub.

## GitHub triggers and Schedule dispatch

Hub-host configuration supplies `fromUsers`, `mention` (default `@pie`), and
`label` (default `pie`). It is not configuration from the target repository.

| Event                                           | Match, after signature and allowlist checks               |
| ----------------------------------------------- | --------------------------------------------------------- |
| `issue_comment` / `pull_request_review_comment` | Comment contains the configured mention                   |
| `issues` labeled                                | Added label equals the configured label, case-insensitive |

A Schedule has one optional trigger: absent or `{ kind: "local" }` keeps today's
local `cron` / `every` / `once` / `manual` behavior. V1 adds
`{ kind: "github", mention?: string, label?: string }`, with `spec: manual` and
per-row overrides of Hub defaults. No migration is needed for absent triggers.

- Creating a GitHub trigger without a relationship fails `InvalidSchedule`.
  The Scheduled UI disables it until enrollment exists.
- The daemon's local tick loop skips non-local triggers. Hub matches only the
  latest advertised enabled rows and dispatches `scheduleId` through
  `ScheduleService.fire` with `reason: "github"`.
- Prompt, worktree, and session policy remain owned by the Schedule. Pause,
  failure circuit, and `maxRuns` still apply at dispatch, not just advertisement.
- No matching Schedule yields `no_schedule`, a recorded delivery outcome, and
  no ad-hoc session. Unknown repository yields a routing error; an offline
  relationship yields `daemon_not_connected` without deferred execution.

The daemon advertises normalized `owner/repo` remotes from registered Projects.
HTTPS and SSH git remote URLs normalize to the same repository. Hub indexes
remote → relationship and rejects a second daemon advertising the same remote.
On dispatch, the daemon resolves the matching Project locally (first matching
origin/fetch URL); no match fails without a session. Worktree creation uses the
existing session-create path; git failure must not leave a session record.

## Wire protocol and reconnect

Tagged frames in the shared contract:

| Direction / frame                         | Payload and purpose                                                                                                            |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Daemon → `hub.hello`                      | `relationshipId`, remotes, enabled GitHub schedules with id/remotes/full trigger; replaces the socket's advertisement snapshot |
| Hub → `hub.execution.create.request`      | `executionId`, `scheduleId`, optional untrusted GitHub context (body, issue title/number/URL)                                  |
| Daemon → `hub.execution.create.response`  | `executionId`, resulting `SessionRef` and optional workspace, or error                                                         |
| Hub → `hub.execution.control.request`     | `executionId`, action `interrupt` or `archive`                                                                                 |
| Daemon → `hub.execution.control.response` | `executionId`, action, success                                                                                                 |
| Daemon → `hub.execution.event`            | Sparse `started` / `idle` / `failed` progress, not the session event stream                                                    |

Hub mints `executionId`; it is not a session id. The daemon persists
`executionId → SessionRef`. Retried create returns the same ref without another
prompt. Create/control can be retried across reconnect; transient progress is
not replayed. There is no second runtime table or Hub-owned conversation history.

`hub.hello` is a full replacement, not a once-at-connect message. Re-advertise on:

- connect/reconnect;
- creation, update, or deletion of a row that is or was Hub-facing, including
  switching to/from a GitHub trigger;
- pause/resume or `maxRuns` pause (paused rows disappear);
- changes to registered Project remotes.

`HubConnector.advertise()` is the only hello writer. Mutations invoke it after
local persistence. Local-only Schedule changes do not advertise. While offline,
keep no hello queue: reconnect sends the current snapshot. Hub neither polls nor
stores a second copy of the job definition.

## Session origin and write-back

An optional daemon-owned session floor field, `source: { kind: "hub", executionId }`,
can support an origin badge. It is written only when Hub creates the session,
never overlaid from Pi, and requires no backfill. Do not put GitHub issue numbers
or Schedule origin on session metadata; Schedule run records already hold the
session relationship. Session title keeps the existing first-prompt behavior.

All GitHub write-back uses the daemon's `GitHubCliAdapter` / local `gh` login,
not a token minted by Hub. Proposed feedback is 👀 on acceptance, 🚀 on create
acknowledgment, 👍/👎 on terminal status, and a completion comment/PR link. Missing
or logged-out `gh` reports `writeback_failed` but does not stop the session;
the user can still inspect it in Pie. PR creation is not automatic unless the
prompt asks for it.

Sessions appear in the existing project list. V1 has no Hub dashboard or PR-panel
chrome; enrollment status, Hub logs, and the GitHub thread are its operator views.

## Persistence

Use `@getpie/effect-json-store` version-1 `{ version, data }` envelopes. These are
proposed host writes and must pass the [host-write review gate](../host-persistence.md)
when implemented; they are not an approved shipped inventory.

| Home / path                                | Stored data                                                                                                                                           |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hub `config.json`                          | Non-empty `fromUsers`, default mention and label                                                                                                      |
| Hub `operator.json`                        | Single operator id/login, password verifier, creation time; no raw password                                                                           |
| Hub `relationships.json`                   | At most one relationship; credential hash, normalized remotes, creation/last-hello times                                                              |
| Hub `deliveries/<deliveryId>.json`         | Delivery/execution/relationship/Schedule identifiers, repository, GitHub event/actor/issue/URL, status/error and timestamps; not a session transcript |
| Daemon `hub/login.json`                    | Operator login keyed by Hub origin; logout affects only this file                                                                                     |
| Daemon `hub/relationship.json`             | Origin, relationship id, raw credential (`0600`), creation time                                                                                       |
| Daemon `hub/executions/<executionId>.json` | Execution id, complete SessionRef, creation time; durable retry mapping                                                                               |

Hub bind port and webhook secret stay in `PIE_HUB_PORT` and
`PIE_HUB_WEBHOOK_SECRET`. Hub never reads the daemon enrollment directory.
Delivery states distinguish acceptance, `no_schedule`, offline/create failure,
started, idle, and failure. They are dispatch records, not another Schedule store.

## Delivery and proof

Land a stack, one concern per PR:

1. **Contract:** wire schemas and optional Schedule trigger, using existing glossary.
2. **Schedule:** persist trigger, local-tick exclusion, relationship validation,
   and `fire(reason: "github")`; no networking.
3. **Dispatch:** create → Schedule fire, durable idempotency, optional session origin;
   callable without the Hub package.
4. **Connector:** enrollment, hello/re-advertisement, reconnect, retry handling.
5. **Hub:** separate package/binary, signed webhook matching, delivery records,
   fail-closed offline behavior; no Hub-side Schedule collection.
6. **CLI enrollment**, then **write-back**, then **UI** as separate slices.

Proof has three distinct gates; fixtures do not establish live GitHub delivery:

- **Repository:** package tests and turbo typecheck, signed HTTP/socket fixtures;
  UI changes use isolated `pie-verify web` and screenshot/video evidence. Test
  invalid signature/actor, missing Project/Schedule, paused/limited Schedule,
  offline/reconnect, and duplicate execution without another prompt.
- **Two-machine lab:** isolated Hub/daemon homes and HTTPS (a Tailscale MagicDNS
  certificate is sufficient). Enroll, create a GitHub Schedule after connect,
  verify hello updates, send a signed fixture from another node, and observe a
  real session. Pause the row and prove the same fixture yields `no_schedule`.
  Invalid signatures/actors or an offline socket must not create a session.
- **GitHub.com:** public HTTPS via Funnel or another public endpoint to the same
  Hub, then a real `@pie` comment / `pie` label on a throwaway registered repo.
  Require Hub feedback, daemon session, and local-`gh` write-back. Tailnet-only
  success is not this proof. If public ingress is unavailable, mark this gate
  blocked; the lab remains the dispatch merge bar, not a claim of live support.

Never enroll the daily daemon or use real homes for fixtures. Cleartext remote
`http://100.x` is still rejected. Opening the Pie SPA is not Hub verification.
The remaining lab decision is which HTTPS host/public endpoint is available.

## Excluded and rejected approaches

- Webhooks on `pie serve`, or Hub as another server composition root: would couple
  public ingress to the privileged UI/Pi runtime and its installation.
- YAML workflows, step graphs, or a second Schedule product: existing Schedule
  owns the job; GitHub supplies only its trigger.
- Slack/other sources, Hub-hosted clocks, pull transport, Worker/DO hosting,
  offline queues, multi-tenancy, and SQL storage: outside V1. Do not prebuild
  interfaces, variants, or deployment plans for them.
- GitHub App installation tokens, cloning unknown repositories, a second agent
  runtime, and a second history stream: outside this proposal.
- GitHub Actions or a direct Paseo port: neither supplies this existing Pie
  Project/Schedule/SessionRef model on the enrolled machine.
