# Session PR：尽早关联，按需更新

## 状态与范围

**实施已落地，自动化检查通过；完整产品验收尚未完成。** 原问题排查的 Pie 代码基线为 `80078b14`。实现与验证范围见文末记录。

本方案取代此前的“daemon 常驻同步”草案。核心规则只有两条：

1. **Agent 在执行过程中尽早登记已知 PR，关联立即持久化。** 登记不额外查询 GitHub，不读取或展开 Stack。
2. **用户真正使用相关 UI 时才更新远端数据。** Renderer 声明需求，Server 统一去重、调度、查询和保存；没有需求，不运行周期 GitHub 同步。

关联存在、Agent 正在运行、daemon 存活，都不代表存在远端更新需求。

范围包含多 PR 关联、Agent 登记、原生 Stack 自动补齐、分支链推导、统一侧栏与关联 PR 面板，以及需要用户确认的 Stack merge / rebase。**暂不做用户手动添加关联的 UI，也不做手动绑定当前分支的 UI。** 保留取消关联作为误关联的纠正入口。

不扩展到多 provider、webhook、全局 PR 数据库、通用任务调度平台或新的 PR 创建界面。Agent 可继续使用现有工具创建 PR，再登记结果。

本文是已确认的实施规范；[GitHub PR V1](github-pull-request-integration.md) 为历史设计，其 CLI 安全边界、写操作确认和实时 head 校验仍须保留。[t3code 最新源码调研](../research/t3code-multiple-pull-requests-and-stacks.md)记录参考依据，不能将上游无客户端需求的周期同步搬进 Pie。

## 1. 问题与完成标准

原始问题集中在：

- `packages/server/src/rpc/pull-request.ts` 的 `statuses` 在批量 RPC 内访问 GitHub，一项失败可使整批失败；有旧身份时不再发现新 PR，发现结果也不持久化。
- `current` 查询成功才追加身份；侧栏选中行优先使用它，未选中行使用 `statuses`，导致点击才出现和切走回退。
- `staleTime` 不等于周期刷新，现有事件恢复也不覆盖 PR 状态。

这些机制已用隔离探针验证，不等于实际 GitHub / UI 验收。

**完成标准：**

- Agent 得到 PR 身份就能登记；工具确认成功即表示已落盘，不等整轮结束。
- 无 UI 需求时，登记、turn-end、Server 启动和重启均不产生额外 GitHub 同步查询。
- 用户看见侧栏中的 Session 行即可产生需求，不必逐个点击 Session。
- 同一 Session 无论是否选中，使用同一组关联、状态和 Stack 数据。
- 多个 Renderer / Session 引用同一 PR，不增加重复的远端读取。
- 失败、断网和重启不清除关联与已有快照；未知状态不伪装成已确认无 PR。
- 多 PR 不自动等于 Stack；取消的关联不会被发现或 Stack 展开加回。
- Stack 写操作独立于关联和读取，必须经过确认及实时校验。

## 2. 三条路径，不互相偷带副作用

```text
Agent 创建 / 实际处理 PR
        |
        v
当前 Session 的登记工具 ──> Session service 校验、去重、落盘
                                         |
                                  通知关联已变化
                                         |
                                UI 可展示已知身份

可见侧栏 / 活动 PR 面板 ──> Renderer 声明当前需求
                                         |
                                         v
                            Server 唯一 PR 同步协调器
                        先读快照，再刷新 stale / dirty 项
                                         |
                              GitHub 摘要 / Stack / 详情
                                         |
                                保存结果并通知 UI

用户确认 merge / rebase ──> 实时读权限、成员及 head ──> 执行写操作
```

登记只写关联并标记需要核验；不自行排一次不受需求约束的 GitHub 任务。若该 Session 此时恰好已在用户可见范围，已有需求可以驱动后续刷新，二者仍是独立路径。

显式 Refresh / Retry、用户请求的 CLI 读取和已确认写操作属于一次性使用，不需要为了完成它们伪造永久 UI 需求。Agent 正在执行用户要求的 `gh` 操作也不受禁止；这里限制的是产品额外发起的状态同步。

## 3. Agent 登记：早、明确、受 Session 约束

拟增加三个 Agent 工具入口：登记 PR、列出本 Session 关联、取消关联。工具名称和 Pi 接入文件在实施时核对实际运行通道；**写入提示词不算完成，必须验证真实 Agent 调用能够到达 Server 并收到落盘确认。** 不为此照搬 t3code 的 MCP 架构。

### 3.1 调用时机

- 创建 PR 成功拿到 URL 后立即登记。
- 开始实际修改或 review 已有 PR 时登记。
- 处理多个 PR 或 Stack 时，每个已知成员分别登记，不只登记最后的 checkout 或 Stack 顶层。
- 一轮结束前列出关联并补齐遗漏；这只是兜底，不取代即时登记。
- 仅在背景信息中提及的无关 PR 不登记。
- 登记失败明确报告；不得把 GitHub 创建成功等同于 Session 关联成功。

不通过扫描聊天文本、解析任意 shell 输出或观察 `gh` 字样来猜关联。产品以后若已有结构化 PR 创建结果，可调用同一个登记方法，但不能另建事实源。

### 3.2 身份与安全

Server 通过受限调用上下文确定完整 `SessionRef { projectId, sessionId }`；不信任模型自行填写的 Session 身份，不给子进程全局 daemon 管理权限。登记权限只覆盖当前 Session 的关联操作，不能借此 merge 或修改其他 Session。

输入仅接受可验证的 GitHub PR URL / 结构化身份；离线校验协议、host、仓库和正整数编号，拒绝凭据、危险路径、任意 CLI 参数与未经允许的 host。跨仓库关联可以保留，但必须在 Server 已允许的 GitHub host 范围内。登记无需网络证明 PR 当前存在；身份合法不等于远端已核验。

重复登记保持原关联时间和顺序，不产生重复项，不清除快照。工具返回“已关联 / 已存在 / 已排除 / 失败”，不把“尚未查状态”当成登记失败。登记与列出均不要求启动另一个 Pi 进程。

### 3.3 取消与恢复

取消关联只改变 Session 的关联，不关闭 GitHub PR。保存排除标记，UI 隐藏该项；分支补漏、Stack 自动展开和普通重复登记都不能清除此标记。

列出工具同时说明哪些身份已被排除，避免 Agent 的结束前补漏将其加回。只有明确恢复操作才可解除排除；Agent 不应仅因它仍在远端 Stack 中就恢复。先前在途的查询结果也不能复活已排除项。

## 4. 保存什么，不保存什么

继续使用 `storage/sessions/<projectId>/<sessionId>.json`，Session service 是唯一元数据写入者，不新建数据库。

```text
Session.pullRequests[]
├─ ref                  host / owner / repository / number
├─ source               agent / branch / stack
├─ linkedAt             首次关联时间，不代表 Stack 顺序
├─ excluded             用户已取消，禁止自动加回
├─ snapshot | null
│  ├─ lifecycle / title / headBranch / baseBranch
│  └─ checkedAt         Server 最近成功核验时间
├─ stack | null
│  ├─ native stack id / number / base
│  └─ layers[]          host 返回的由底到顶成员身份与顺序
└─ stackCheckedAt | null 最近成功核验拓扑的时间，成功确认无 Stack 也记录
```

- PR 身份按规范化 host / 仓库和编号去重；分支名保留大小写。
- URL 从校验后的身份生成，不重复保存任意外部 URL。
- `snapshot: null` 是身份已知、状态未取得，不伪装成 open。
- 原生 Stack 保存有界的成员摘要和顺序，不复制完整 PR 详情。没有原生 Stack 时展示独立 PR，不推导 chain。
- 网络错误不能清除旧 snapshot / stack；成功确认没有原生 Stack 才更新为空，并保留本次成功检查的新鲜度记录。未知、无 Stack、查询失败必须可区分。
- 成功核验更新时间，即使状态内容没变；按 Session 合并落盘，不因窗口数量增加写入次数。Agent 提供的状态文字不冒充 Server 核验快照。
- checks、review、权限和 head SHA 的完整详情按需读取，不将它们全部固化到 Session 元数据。展示快照绝不作为写操作授权。
- demand、排队、失败退避和 dirty generation 是 Server 临时状态，不写持久任务。重启后保留快照，首次有需求时重新核验，而不是启动时补查。

## 5. 什么算“用户实际使用”

| 场景                                        | 需求范围 / 行为                                               |
| ------------------------------------------- | ------------------------------------------------------------- |
| 可见窗口内，侧栏实际显示某些 Session 行     | 这些行的关联摘要与紧凑 Stack 拓扑；不要求选中 Session         |
| 项目折叠、侧栏关闭、行滚出可视区            | 撤销相应行需求；不因列表已经缓存而继续刷新                    |
| PR / Stack 面板正在展示                     | 面板当前 Session 的关联列表，及当前所选 PR / Stack 的所需详情 |
| 面板 tab 存在但未显示，或只预加载了页面数据 | 不产生详情需求                                                |
| 页面隐藏、窗口最小化或关闭                  | 撤销该窗口需求；其他仍可见窗口不受影响                        |
| 窗口失去焦点但仍可见                        | 不必仅因 blur 撤销；不是用焦点代替可见性                      |
| Agent 登记、turn-end、daemon 启动           | 本身均无需求                                                  |
| 用户 Refresh / Retry、明确 CLI 读取         | 一次性需求，完成即结束                                        |

可见性用当前列表与窗口生命周期表达；复用已有 viewport 信息，无现成机制时用平台可见性能力，不为每一行增加轮询计时器。Desktop 的最小化 / 可见性通过既有平台边界提供，不能让共享 app 直接依赖 Electron。

### 5.1 有界需求生命周期

拟使用每 Renderer、每 ServerConnection 一份**临时需求租约**：替换当前需求集合，Server 返回租约标识；同一窗口内侧栏和面板取并集。Session 一律使用完整 SessionRef，详情需求额外带明确 PR 身份。

- 有需求时每 30 秒续租，90 秒未续租自动过期；这是本地需求保活，不是 GitHub 轮询。续租不将所有项标记 dirty，也不绕过新鲜度。
- 需求变化立即替换；集合为空时立即释放并停止续租。正常隐藏 / 关闭主动释放；崩溃、断网或未成功释放时最多由租约到期回收。
- 租约属于已认证的调用上下文，不能修改其他客户端的租约；引用逐项校验，限制集合大小，不接受原始工作目录。
- 需求变更按窗口串行并带递增版本，Server 拒绝旧版本覆盖；释放或过期的租约不能被迟到续租复活。重新申请前必须重新检查当前可见需求。
- 重连重新声明需求并补读状态；Server 重启丢弃所有租约，不恢复上一次窗口的需求。
- 多窗口需求由 Server 合并，同一项只有一个在途读取。新租约 / 续租不重置已有 PR 的 freshness。

选择租约是为了给浏览器冻结、丢失关闭消息和半断连一个明确上界；不另建每 Session 的后台任务或永久订阅表。30 / 90 秒为初始常量，验收使用可控时钟。

### 5.2 首次使用与停止

首次需求先返回已存关联和快照，不等待 GitHub。首次未核验、过期或 dirty 的项由 Server 排队；新窗口请求仍新鲜的数据不重复查询。

最后一份需求消失或过期后，删除未开始的自动任务，停止周期查询；已经启动的有超时读取可以结束并安全保存，但不得继续分页、展开兄弟查询、重试或排下一轮。某 PR 仍被其他可见 Session 需要时保留共享工作。显式用户操作不因窗口隐藏被当作自动读取取消，尤其不能掩盖已经发出的写操作结果。

## 6. Server 唯一协调器

在 `packages/server/src/pull-request/` 增加一个窄协调器，于 `rpc/runtime.ts` 组合一次，复用同一个 Session service 和 EventBus。服务可随 Server 存活，但没有需求时不运行 GitHub due-work 循环；租约回收与本地事件处理不算远端同步。

### 6.1 触发规则

| 触发                      | 无需求                     | 有相关需求            |
| ------------------------- | -------------------------- | --------------------- |
| 新关联落盘                | 标记未核验，不查 GitHub    | 排所需摘要 / 拓扑读取 |
| turn-end（含失败 / 取消） | 仅标记 dirty               | 合并为一次到期刷新    |
| 工作分支 / 远端上下文变化 | 标记发现入口 dirty         | 校验归属后补漏发现    |
| 取消关联、删除 Session    | 清理待办与需求，不远端写入 | 同左，并通知 UI       |
| Server 启动 / 重启        | 恢复可读快照，不远端扫描   | 等新需求建立后核验    |
| 外部 GitHub 变化          | 不主动追踪                 | 周期到期时发现变化    |

事件只排本地状态变更，不在聊天事件处理锁里等待 `gh`。一次读取开始时记下 dirty generation；读期间有新的工作完成事件，旧结果不能将新一代 dirty 清除。没有剩余需求时保留 dirty，等下次实际使用。

### 6.2 仅在有需求时适用的节奏

| 数据                       | 初始节奏                                                    |
| -------------------------- | ----------------------------------------------------------- |
| 未核验、dirty 摘要         | 尽快排队，受去重、并发和退避约束                            |
| open / draft 摘要          | 60 秒到期                                                   |
| closed 摘要                | 15 分钟到期，覆盖 reopen                                    |
| merged 摘要                | 不周期读取；重启后首次使用、dirty 或显式刷新可核验          |
| 原生 Stack 拓扑            | 首次使用核验；所需拓扑每 5 分钟到期，dirty / 显式刷新可提前 |
| 可信记录分支的补漏发现     | 首次需要时核验，之后每 5 分钟；与历史身份刷新独立           |
| checks / review 等完整详情 | 仅活动面板需要时读取；关闭后不周期刷新                      |

Stack 拓扑有独立到期条件，不能只在 PR 状态变化时查，否则状态没变但层序变化会漏掉。新发现的成员最多补齐必要摘要；展示 Stack 不能偷偷开启整组 PR 的完整详情读取。

自动读取并发上限初始为 **4**，摘要按完整 PR 身份去重，Stack 按已知原生身份去重，分支发现按完整仓库 / head 上下文去重。到期队列只覆盖有需求项；不得对全部历史 Session 扫描 GitHub。分页、成员数量、输出大小均有上限，超限明确显示不完整，不无限展开。

单项失败保留旧结果，其他项独立落盘。网络失败从 1 分钟逐步退到 15 分钟；认证 / CLI 缺失在相应 host / 进程范围冷却；限流遵守可靠的重试时间。自动重试也受需求约束，手动刷新不绕过限流。

### 6.3 分支补漏与并发安全

Agent 显式登记是主路径；可信分支发现是用户使用时的补漏，不承担离线还原所有历史关联的责任。

- 创建 Session 时保存可取得的工作分支。非 Git / detached HEAD 不阻塞聊天，不猜历史分支。
- 只有独占 worktree 可以跟随 checkout；规范化路径，检查全部已知 Session，包括归档项。共享目录保存的分支不跟随其他 Session 的 checkout。
- 默认分支不是扫描所有 base PR 的入口。发现按记录的 head 查询并验证仓库 / fork 来源，歧义时不随意选一条。
- 旧 Session 没有可信分支也没有关联时显示“尚未关联”，不谎称查明无 PR；本轮不增加手动绑定按钮。Agent 可直接登记明确身份。
- 旧 PR 不可访问或已终态，不阻止独立的分支补漏；发现为空不清除已有身份。
- **创建失败清理陷阱：** 普通 Session 开始保存 `gitBranch` 后，不能再以该字段存在决定删除 worktree；必须以“本次实际创建了 worktree”为依据。

网络 I/O 在 Session mutation lock 外；提交时重新校验当前关联、排除标记、分支上下文、归档 / 删除状态，只合并相关字段，保留并发标题 / 模型修改。读盘或写盘失败不得广播“已保存”。已知 PR 查询可从有效 Project 目录按明确身份执行，不要求旧 worktree 仍存在。

归档不会永久删除关联，但不进入侧栏自动需求；用户实际打开归档 Session 的 PR 面板或明确刷新时可以读取，不取消归档。删除后的任何迟到结果都不能重建记录。

## 7. 多 PR 与 Stack 规则

### 原生 Stack

Server 在有需求时通过 GitHub 原生 Stack API 取得层序，并以 `source: stack` 关联缺少的成员。登记仍走同一个 Session service 方法，不能绕过排除标记或并发检查。

新关联只表示该 PR 属于用户正在查看的原生 Stack，不证明它由当前 Session 创建。远端 Stack 移除某层时更新拓扑，不自动删除历史 Session 关联。host 不支持原生 Stack 时展示普通独立 PR；暂时查询失败保留旧拓扑并标记待更新。不推导/不持久化非原生 chain。

### 代表项与展示

```text
侧栏 Session 行                          PR 内容面板
[phase] Session title … [PR / Stack]      关联列表
                                         ├─ Native Stack：底层 → 顶层
单个 PR：编号与状态                      └─ 无关 PR：独立项
多个无关 PR：代表 PR + 额外数量           当前所选 PR 的详情与允许操作
原生 Stack：Stack 标识 + 层数
```

优先未完成 / 未核验工作；单条原生 Stack 选择最高未完成层，全终态仍指向顶层。多个无关项按首次关联时间选择未完成代表项，不用请求完成顺序；这只是导航规则，不声称是一个 Stack。聚合状态保留 unknown，不能把尚未核验解释为全部已合并或全部 open。

所有侧栏行读同一个 Server 投影，删除 active-row 的 `current` 覆盖。未知状态保留中性 PR 标识；有旧快照的错误保留上次状态，显示核验时间与 Retry。键盘可获得同样说明，操作不能嵌套交互元素或触发 Session 行导航。

关联 PR 面板按用户选定的明确身份读取，不再悄悄替换成当前 checkout PR。现有 `current` 如保留，只用于明确标注的 Current branch PR 入口，不再顺便写关联或覆盖侧栏。选中状态存 PR 身份，不复制整份 Server 对象。

## 8. RPC、事件与更新恢复

拟议边界按职责划分，不另建一套远端数据缓存：

- Agent 受限登记 / 列出 / 取消入口：只处理关联，不代表远端核验。
- `pullRequest.statuses({ refs })`：只读关联快照和同步状态，每项独立结果，不执行 GitHub fan-out，也不因被预取而建立需求。
- 需求租约入口：申请 / 替换 / 续租 / 释放当前可见集合；只有这里及明确一次性使用可以让协调器执行到期读取。
- 明确身份的详情、Refresh / Retry、确认后的 PR / Stack 写操作：分别校验引用和权限，不能复用展示快照当授权。

复用 collection event `session.pull-requests.updated` 通知关联、快照或可见同步状态变化，携带完整 SessionRef。持久化先于通知；内存错误 / 恢复转换也通知，重复相同错误不持续广播。事件本身不是新的 GitHub 刷新触发器。

沿用唯一全局消费者 `useSessionListSync` 和 TanStack Query：合并失效后补读 `statuses`，不在 feature 间互相导入 hook，不恢复每行或每窗口的 GitHub 轮询。租约保活不保存另一份 PR 数据。

首次建立或重建事件订阅后补读，覆盖“查询完成、订阅建立前”的更新；若通知到达时读取仍在途，完成后再补读一次。重连同时重新声明可见需求；缓存必须按 ServerConnection 与完整 SessionRef 隔离。失焦 / focus 的纯状态补读不能绕过需求门控。

## 9. Stack merge / rebase：包含在方案中，独立验收

识别、关联、自动补齐均不得触发 GitHub 写入。用户选择 action 后，显示目标 Stack、涉及成员、合并策略或重写风险；确认后 Server 再实时读取。

- 校验当前关联未排除、host 能力、用户权限、最新原生层序，以及每个受影响层的 expected head。变化时拒绝并要求重新确认。
- Merge stack 只覆盖所选层及其下方未合并成员，不对全部历史关联盲目 merge。使用 host 支持的原生操作；缺少必要保护时禁用，不退化成无保护循环。
- Rebase stack 按底到顶更新远端分支，预检各层权限，用 expected head 防止覆盖新提交，并检查已处理层是否再次变化；不改本地 checkout。
- 没有原生 Stack 时禁用 Stack 批量写操作。
- 超时或不可确认结果不得自动重复写入；中途失败明确报告哪些层已完成，不伪装成原子操作，不自动回滚远端历史。
- 保留现有单 PR merge / auto-merge 的实时上下文校验与 `--match-head-commit`，不因支持关联面板而削弱它们。

执行中为确认该操作结果所需的有界读取属于这次用户操作。结束后仅标记相关数据 dirty；仍有 UI 需求才继续状态同步。后续刷新失败不能把已确认成功的写操作变成失败。

## 10. 实施顺序与验收

沿用现有 `docs/design/`，不为本功能另建任务管理框架。以下步骤串行接通真实路径；不只交付孤立 helper。

### 第一步：关联存储与真实 Agent 登记

涉及 contract、`harness/session-{service,repository}.ts`、Server 类型和实际 Agent 工具接入边界。

验收：真实 Agent 在创建 / 处理 PR 后完成落盘；重复不增项，越权 Session / host 被拒绝；列出与取消无 GitHub 查询；写盘失败准确返回；旧数据无损读取；恢复运行继续使用原 SessionRef。保留对已排除项的尊重。

### 第二步：需求门控与统一侧栏

涉及 `pull-request/` 协调器、RPC runtime / handlers、需求租约、`statuses`、侧栏和全局事件恢复。必要时补齐窗口可见性的既有平台接口。

验收：零需求启动 / 登记 / turn-end 的同步 GitHub 调用数为零；侧栏可见行不用点击即更新；新鲜数据不因第二个窗口重复读取；隐藏立即释放，异常断连在 90 秒内回收；最后需求消失后不继续自动派生任务；单项失败不影响其他项；重连和在途通知不丢更新。PR 同步不启动 Pi。

### 第三步：Stack 与关联 PR 面板

加入所需摘要字段、原生拓扑、自动成员补齐、代表项选择和按明确身份的详情。

验收：Agent 可在无 UI 时登记每层但不查 Stack；用户查看后才补齐远端成员；层序不是 PR 编号顺序；无关 PR、环、重复 head 和分叉不伪装成单 Stack；取消项不复活；远端拓扑变化而 PR 状态不变也能在有需求时更新；非活动面板不拉详情。

### 第四步：Stack 写操作

接入确认 UI、权限 / 预期成员与 head 校验、host 操作和部分失败反馈。

验收：未经确认不执行；确认期间成员或 head 变化被拒绝；中途失败不重试已完成写入；结果未知时不重复提交；本地 checkout 不变；非原生关联不可执行原生 Stack action。真实 GitHub 写入验收必须使用用户授权的测试仓库。

### 总体验收

运行受影响包的 Turbo test / typecheck / lint；React 改动执行 react-doctor；用 `pie-verify web` 和 `pie-verify desktop` 验证可见性、切换、断网、重启、多窗口与确认操作，按仓库规则附截图 / 短视频，不提交媒体文件。

必须覆盖：正常与不可用目录混合、共享目录 checkout 不串关联、普通 Session 创建失败不删除项目目录、fork / 多 remote 歧义、归档面板读取不取消归档、删除 / 取消期间迟到结果不复活，以及无需求时没有认证 / 限流重试风暴。

小规模目标：10 个有需求 Session、最多 10 个唯一 PR、单次 host 读取 5 秒内且无退避时，首次核验及 open 状态外部变化在 120 秒内可见；分支补漏与拓扑周期更新按 5 分钟节奏。**计时从实际需求开始，不从 daemon 启动或 Agent 登记开始。** 超限、断网或限流应显示待更新 / 不完整，而非假装没有 PR。

文档完成不代表实现完成；所有上述真实调用链与验收通过后，才可标记产品交付。
